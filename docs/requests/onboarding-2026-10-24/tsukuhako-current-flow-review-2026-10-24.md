# ツクハコ：現状の導線確認と改善方針

確認日：2026年10月24日（日本時間）  
対象：Linux版0.4.5の作業ブランチ `codex/linux-deb-045-20261024`  
確認コミット：`24e3b852f8357c05e59814bec9ee9a7c9f4a2dca`  
位置づけ：現状の簡易レビューと考察。コード変更・正式な修正依頼の送付はしていません。

## 1. 結論

**改善点はあります。優先したいのは、初回の目標を「サンプル画面を表示する」にそろえ、そのための案内を一つの流れにすることです。**

現在も、用途から選べる画面、詳細設定の折りたたみ、不足分の診断、生成先に合った手順、内蔵ガイドがあります。これらを活用しながら、次の点を整えるのが妥当です。

1. F2などの管理用の名前を、通常の案内で理解させない。
2. 「今足りないもの」と「後の工程で行うこと」を分けて表示する。
3. 初回の画面表示と、その後の変更・復元の練習を分ける。
4. 生成後の主な案内を一つにし、保存先やURLを引き継ぐ。
5. 初回の手順から、詳しい検証履歴や別OSの参考情報を分離する。

特に重要なのは、**Dev Containers拡張の確認は必要な確認であり、生成される設定ファイルの確認とは別だった**という点です。一方、別項目の「Dev Container起動：未確認」は固定表示なので、その段階で解消すべき不足のように見せる必要はありません。

## 3. 現在の導線

通常の入口は、次の流れです。

**debで導入 → メニューから起動 →「作る」画面 →「はじめて使う」または開発準備チェック → 構成選択 → 保存先 → 内容確認 → ファイル作成 → 起動の手順 → VS Code → 初期処理 → ブラウザー表示**

| 場面 | 現在の実装・案内 |
|---|---|
| インストール | Linuxは単体deb。メニューから起動し、内蔵ガイドを読める |
| 起動直後 | 「作る」画面。「はじめて使う」の入口と、その下に開発準備チェックがある。Linuxでは準備確認が自動で走る |
| 構成選択 | 「画面を作りたい」など5用途から選ぶ。画面づくりの初期候補はNext.js／F2 |
| 作成 | 保存先と新しいフォルダー名を指定し、確認して生成。識別ラベルやポートは詳細設定にある |
| 生成完了 | 「最初の一歩」「この生成結果の手順」「VS Codeで開く」「手順をコピー」「READMEを見る」が並ぶ |
| 開発開始 | 生成先の手順でホスト側の診断を行い、VS Codeで開く。Dev Containerを開く操作は利用者が行う |
| 最初の表示 | 初期処理の正常終了を確認して開発サーバーを起動し、今回のURLをブラウザーで開く |

根拠：[初期画面と入口](https://github.com/garchomp-game/tsukuhako/blob/24e3b852f8357c05e59814bec9ee9a7c9f4a2dca/generator-desktop/src/main.tsx#L14)、[用途の定義](https://github.com/garchomp-game/tsukuhako/blob/24e3b852f8357c05e59814bec9ee9a7c9f4a2dca/generator/src/core/catalog.mjs#L4)、[作成後の選択肢](https://github.com/garchomp-game/tsukuhako/blob/24e3b852f8357c05e59814bec9ee9a7c9f4a2dca/generator-desktop/src/Generator.tsx#L82)、[初回手順](https://github.com/garchomp-game/tsukuhako/blob/24e3b852f8357c05e59814bec9ee9a7c9f4a2dca/curriculum/guide/first-run.md#L7)

すでに良い点は、次のとおりです。

- 利用者の用途から選ぶ構造があり、内部番号だけを並べた選択画面ではない。
- 日本語・空白を含む新しいフォルダー名を受け付け、詳細設定も通常の入力から分けている。
- ファイル作成と開発環境の起動を区別している。
- 初回ガイドには、各段階の成功の目印がある。
- 生成直後の教材表示は、今回の保存先・ポートを反映した手順へ差し替える。
- エラー時の次の操作、復旧手順、詳細ログへの入口がある。

これらは維持し、表示の順番と案内の整合性を改善する方針が適しています。

## 4. 改善点と、修正の考え方

### 4.1 F2の説明を増やすより、利用者向けの名前をそろえる

**確認した事実：** F2は、最初の案内、選択内容の表示、確認画面、完了画面、ガイドの見出しに出ています。主な選択肢には日本語の用途説明がありますが、その後も管理用IDを確認するような案内が残っています。

根拠：[開始画面](https://github.com/garchomp-game/tsukuhako/blob/24e3b852f8357c05e59814bec9ee9a7c9f4a2dca/generator-desktop/src/main.tsx#L16)、[選択・確認・完了の表示](https://github.com/garchomp-game/tsukuhako/blob/24e3b852f8357c05e59814bec9ee9a7c9f4a2dca/generator-desktop/src/Generator.tsx#L75)、[ガイドの冒頭](https://github.com/garchomp-game/tsukuhako/blob/24e3b852f8357c05e59814bec9ee9a7c9f4a2dca/curriculum/guide/start.md#L1)

**考察：** 利用者は、目的の名称とF2が同じものだと覚えながら読み進める必要があります。用語集を追加しても、この負担は残ります。

**推奨する修正：** 内部IDは保持したまま、利用者向けの表示名を共通化します。例えばF2は「ページを切り替えるWeb画面を作る」、F1は「一つの画面を作る」など、違いが分かる言葉を候補にします。正確な名称は両構成の提供内容と照合して決めます。

初めての人には、推奨構成で始める入口を用意し、構成比較は別に開ける形が考えられます。Next.jsなどの技術名は、選択に必要な人向けの補足に置けます。外部アプリで実際に探す「Dev Containers」等の名称は、その操作時に用途を添えて示します。

適用する原則：利用者の言葉と表記の一貫性。[SmartHRのライティング指針](https://smarthr.design/products/contents/writing-style/)

### 4.2 Dev Containerに関する二つの表示を分けて直す

**確認した事実：** 現状には、別の意味を持つ二つの表示があります。

| 表示・処理 | 実際にしていること | 改善の方向 |
|---|---|---|
| Dev Containers拡張の確認 | PC側のVS Codeに必要な拡張があるかを確認する。自動導入はしない | 確認機能を維持し、「VS Codeで開くための機能」と用途を先に示す |
| Dev Container起動：未確認 | 実際の起動を確認した結果ではなく、現行画面では固定の未確認表示 | 今の不足項目と並べず、「ファイル作成後に行うこと」として説明する |

拡張の有無は `code --list-extensions` と拡張IDで確認しています。生成される `.devcontainer` 設定とは別です。LinuxではDockerや拡張が準備できていなくても、生成用の条件を満たせばファイル作成へ進めます。Windowsでは生成先となるWSLと同梱補助ファイルの準備が先に必要です。

根拠：[拡張の確認と起動状態](https://github.com/garchomp-game/tsukuhako/blob/24e3b852f8357c05e59814bec9ee9a7c9f4a2dca/generator-desktop/adapters/local.mjs#L47)、[準備画面の固定表示](https://github.com/garchomp-game/tsukuhako/blob/24e3b852f8357c05e59814bec9ee9a7c9f4a2dca/generator-desktop/src/Preparation.tsx#L35)、[作成前確認の固定表示](https://github.com/garchomp-game/tsukuhako/blob/24e3b852f8357c05e59814bec9ee9a7c9f4a2dca/generator-desktop/src/Generator.tsx#L78)、[生成へ進む条件](https://github.com/garchomp-game/tsukuhako/blob/24e3b852f8357c05e59814bec9ee9a7c9f4a2dca/generator-desktop/src/Generator.tsx#L95)

**考察：** 「生成する設定はツールが用意する」という認識は正しい一方、現状の拡張確認には別の役割があります。問題は、同じような用語で、今必要な準備と将来の起動確認をまとめて見せていることです。

**推奨する修正：** 準備欄は、利用者が今判断できる次の情報から示します。

- このPCでファイルを作成できるか。
- 作ったものを動かすまでに、追加で必要なものは何か。
- 不足している場合、次にどの操作をするか。

例えば、該当する状態なら「ファイルは作成できます。動かす前にVS Codeへ機能を追加してください」と説明できます。「Dev Containers」という正式名は、追加する操作のところで表示します。

現行の不足項目のリンクはOS別の準備章へ移動するため、拡張機能の不足なら拡張の手順へ直接つなぐと、探し直す負担を減らせます。診断の詳細は残し、通常は不足と対処を先に見せます。

準備確認を一律に生成後へ移す必要はありません。開始時に必要条件を知らせつつ、生成に必須な条件と実行前に満たせばよい条件を区別します。固定の「未確認」を、根拠なく「確認済み」へ変える修正にはしません。

適用する原則：実際の状態に対応する表示と、その時点に必要な説明。[W3Cの工程表示指針](https://www.w3.org/WAI/WCAG2/supplemental/patterns/o1p04-clear-steps/)、[VS Code公式の設定・拡張の区別](https://code.visualstudio.com/docs/devcontainers/containers)

### 4.3 初回の完了条件を、すべての入口でそろえる

**確認した事実：** 新しい初回ガイドは、ブラウザーで最初の画面を表示するところまでを目標とし、変更・復元を任意にしています。一方、全体の案内表示、生成完了画面、生成される `START_HERE.md` は変更・復元までを続きの流れや完了条件にしています。

根拠：[ガイドの到達点](https://github.com/garchomp-game/tsukuhako/blob/24e3b852f8357c05e59814bec9ee9a7c9f4a2dca/curriculum/guide/first-run.md#L95)、[全体の案内](https://github.com/garchomp-game/tsukuhako/blob/24e3b852f8357c05e59814bec9ee9a7c9f4a2dca/generator-desktop/src/main.tsx#L15)、[生成後の説明](https://github.com/garchomp-game/tsukuhako/blob/24e3b852f8357c05e59814bec9ee9a7c9f4a2dca/generator-desktop/src/Generator.tsx#L90)、[生成手順の完了条件](https://github.com/garchomp-game/tsukuhako/blob/24e3b852f8357c05e59814bec9ee9a7c9f4a2dca/generator/src/core/next-steps.mjs#L65)

**考察：** 「どこまで進めれば、まず使える状態になるか」が入口ごとに変わります。学習として有用な変更・復元が、利用開始の必須条件に見える可能性もあります。

**推奨する修正：** 次の三つの達成を区切り、名前を統一します。

| 達成 | 表示する内容の例 |
|---|---|
| ファイル作成の完了 | 「開発用フォルダーを作成しました。次はサンプル画面を表示します」 |
| 初回利用の達成 | 「サンプル画面が表示されました。ここまでで、最初の準備は完了です」 |
| 次の任意練習 | 「文字を一か所変えてみる」「元に戻してみる」 |

自動確認できない達成は、画面に現れる目印や本人の確認として扱います。実装上の自動検出と利用者による確認を混同しません。既にある初期処理の正常終了確認は省略しません。

適用する原則：到達点を先に示し、操作の結果を確認できるようにする。[Diátaxisのチュートリアル指針](https://diataxis.fr/tutorials/)

### 4.4 生成後の案内を、一つの分かりやすい入口へまとめる

**確認した事実：** 生成完了画面には複数の案内が並びます。「この構成の『最初の一歩』を読む」は内蔵Readerを開き、今回生成した保存先・ポート入りの手順を表示します。「この生成結果の手順を見る」は、同じ手順データを生のMarkdownとして表示します。後者にはリンクが使えない旨の説明があります。

根拠：[生成後のボタンと文書表示](https://github.com/garchomp-game/tsukuhako/blob/24e3b852f8357c05e59814bec9ee9a7c9f4a2dca/generator-desktop/src/Generator.tsx#L85)、[今回の手順への差し替え](https://github.com/garchomp-game/tsukuhako/blob/24e3b852f8357c05e59814bec9ee9a7c9f4a2dca/generator-desktop/src/Reader.tsx#L22)

**考察：** ボタン名から、二つの手順の違いや、どれを読むべきかを判断しにくい構造です。さらに初回ガイドでは、保存先とURLをメモして別の案内から使うよう求めています。[保存先・URLを引き継ぐ現在の手順](https://github.com/garchomp-game/tsukuhako/blob/24e3b852f8357c05e59814bec9ee9a7c9f4a2dca/curriculum/guide/first-run.md#L50)

**推奨する修正：** 主な入口を「サンプル画面を表示する手順へ」などに統一し、既存Readerで今回のプロジェクトに合う続きが読めるようにします。

その手順内で、必要になる順に「VS Codeで開く」、実際の保存先、コピーするコマンド、実際のURLを示します。README、手順全体のコピー、技術の説明は補助の入口へ分けます。既に読みやすいReaderがあるため、初回改善のためだけに新しい文書ビューアを作る必要はありません。

新しい初回ガイドへのリンクに差し替えるだけでは、現在のReaderが持つ保存先・ポートの反映を失う可能性があります。**今回の生成結果を引き継ぐ機能と、短い初回の順路を一緒に保つ**ことが必要です。

再起動後に生成結果の状態は保持されないため、将来は「作ったプロジェクトを開く」入口も検討できます。ただし、まず同一セッション中の案内統合を優先し、保存や復元の新機能を初回改善の必須条件にはしません。

適用する原則：推奨経路を明確にし、利用者の記憶に頼る情報を減らす。[Googleの手順作成指針](https://developers.google.com/style/procedures)、[NN/gのユーザビリティ原則](https://www.nngroup.com/articles/ten-usability-heuristics/)

### 4.5 操作の案内から、検証履歴と別OSの参考情報を分ける

**確認した事実：** 内蔵ガイドの入口には、旧Linux版、Windowsの既存配布物、Server CIと実機の違い、新debの確認状況などが並びます。初回手順にはLinuxとWindowsの段落があり、旧版で確認した終了表示の説明もあります。

根拠：[入口の対象・確認範囲](https://github.com/garchomp-game/tsukuhako/blob/24e3b852f8357c05e59814bec9ee9a7c9f4a2dca/curriculum/guide/start.md#L25)、[OS別準備](https://github.com/garchomp-game/tsukuhako/blob/24e3b852f8357c05e59814bec9ee9a7c9f4a2dca/curriculum/guide/first-run.md#L17)、[過去の確認環境の説明](https://github.com/garchomp-game/tsukuhako/blob/24e3b852f8357c05e59814bec9ee9a7c9f4a2dca/curriculum/guide/first-run.md#L79)

**考察：** 検証の区別は開発・提供判断には重要ですが、次に押すものを探している人には情報が多くなります。すでに起動したアプリ内で、受取からインストールまでの説明を大きく読む必要もありません。

**推奨する修正：** 内蔵ガイドの冒頭は、現在の対象OS、利用に必要な重要条件、次の操作を短く示します。表示するOSの手順を絞り、他OSの案内は選択して切り替えられるようにします。

詳しい検証履歴、旧版との違い、開発向けの確認記録は「対応環境と確認状況」へ分離します。受取・インストール手順は、導入前の案内と、必要時に開けるヘルプにします。未対応・未確認という提供上の条件まで隠し、対応済みのように見せる変更にはしません。

短い理由や、その操作前に必要な注意は手順の近くに残します。説明を一律に削るより、「今読まないと進めない内容か」を基準に配置を決めます。

適用する原則：補足を分離し、必要情報は隠さない。[デジタル庁のディスクロージャー指針](https://design.digital.go.jp/dads/components/disclosure/)

### 4.6 困った場所から、必要な手順へ直接戻れるようにする

**確認した事実：** 症状別のトラブル案内はありますが、戻り先の一部は「FIRST-RUN 2番」などの平文です。章内の見出しへ移動する仕組みは既にあります。

根拠：[症状別の戻り先](https://github.com/garchomp-game/tsukuhako/blob/24e3b852f8357c05e59814bec9ee9a7c9f4a2dca/curriculum/guide/troubleshooting.md#L25)、[章・見出しのリンク処理](https://github.com/garchomp-game/tsukuhako/blob/24e3b852f8357c05e59814bec9ee9a7c9f4a2dca/generator-desktop/src/links.ts#L2)

**推奨する修正：** 「Dockerを確認する」「初期準備が終わったか確かめる」のような行動名で、該当箇所へ直接移動できるリンクを付けます。利用者にファイル名と手順番号を覚えて探し直してもらう必要を減らせます。

さらに操作を減らす段階では、生成後のホスト診断をアプリから実行できるか検討できます。ただし、生成後の設定に対する確認には役割があるため、生成前の診断と重複して見えることだけを理由に省きません。これは後続の機能改善候補です。

適用する原則：事象と次の行動をつなぐ。[SmartHRのエラーメッセージ指針](https://smarthr.design/products/contents/error-messages/overview/)

## 5. 改善後に目指す案内の形

下表は、今回のコード確認に基づく構成案です。表示名や画面の確定仕様ではありません。

| 場面 | 主に見せる案内 | 詳細へ分けるもの |
|---|---|---|
| はじめて使う | 「このPCでサンプル画面を表示します」＋推奨構成で始める入口 | 他構成の比較、技術の仕組み |
| 必要な準備 | 今の可否、不足しているもの、その項目の手順 | 全診断ログ、接続方式の詳しい説明 |
| 保存先を決める | 保存する場所、新しいフォルダー名 | ポート、識別ラベルなど既存の詳細設定 |
| ファイル作成後 | 「サンプル画面を表示する手順へ」 | README、全手順のコピー |
| 続きの手順 | 今回の保存先・URL、今使うアプリ、操作、成功の目印 | 別の起動方法、設計の背景 |
| 最初の表示後 | 初回達成の確認、終了・次回再開への入口 | 任意の変更・復元の練習、追加教材 |

「準備→作成→開く→画面を確認」の全体像と、ファイル作成画面の4段階は役割が異なります。どちらを示しているか分かるようにし、生成完了を全工程の完了に見せないようにします。

## 6. 次の修正で優先する範囲

まず、既存の仕組みで直せる次の範囲をまとめて扱うのがよいと考えます。

1. **名前と初回の目標をそろえる。** アプリ、ガイド、生成後手順で同じ対象・同じ到達点を示す。
2. **生成後の案内をまとめる。** 今回の保存先・URLを保ち、初回の主経路を一つにする。
3. **準備欄の意味を整理する。** 今必要な不足と、後の工程の未実施を区別する。
4. **初回ガイドを短い操作中心の構成へ再編集する。** 対象OS、操作、結果、困ったときのリンクを残す。

自動インストール、コンテナーの自動起動、再起動後のプロジェクト復元などは、別の機能追加として検討できます。まず案内の整合性を直し、利用者が止まる場所を観察してから追加の自動化を選ぶと、修正範囲を適切に保てます。

## 7. 作業担当へ渡すときに必要な注意

表示される文書には生成元があります。画面で見えた文書だけを個別に直すと、再生成時に戻ったり、他の入口と食い違ったりします。

| 対象 | 主な変更元・確認先 |
|---|---|
| 画面の名前、準備、生成後のボタン | `generator-desktop/src/main.tsx`、`Preparation.tsx`、`Generator.tsx`、`Reader.tsx` |
| 用途・構成の表示情報 | `generator/src/core/catalog.mjs`、`catalog.json` |
| 初回ガイドの正本 | `docs/launch/sunday-pack/*.md` |
| 生成される初回ガイド | `curriculum/guide/*.md`。正本から教材ビルドで作られる |
| 生成プロジェクトの手順・教材の最初の一歩 | `generator/src/core/next-steps.mjs` と、それを使う生成・教材ビルド |
| OS別準備教材 | `tools/build-curriculum.mjs` の原稿と出力先 `curriculum/setup/*.md` |

生成元の関係：[教材ビルドの初回ガイド取り込み](https://github.com/garchomp-game/tsukuhako/blob/24e3b852f8357c05e59814bec9ee9a7c9f4a2dca/tools/build-curriculum.mjs#L28)、[生成手順の組み立て](https://github.com/garchomp-game/tsukuhako/blob/24e3b852f8357c05e59814bec9ee9a7c9f4a2dca/generator/src/core/next-steps.mjs#L55)

修正後は、コードの検査に加えて、次の一巡を確認するのが適切です。

- はじめての入口から、F2の意味を知らずに目的の構成を選べるか。
- 不足している拡張と、ツクハコが作る設定を取り違えないか。
- ファイル作成の前後で、次に必要な操作が分かるか。
- 生成後の主な案内が、実際の保存先・URLを保持しているか。
- 背景説明を開かなくても、初期処理の正常終了とサンプル表示を確かめられるか。
- 変更・復元が任意だと分かり、困ったときに該当手順へ戻れるか。

今回の確認では、文書や画面の不足を補うために、新しい技術を大量に導入する必要は見当たりません。既存の診断、Reader、動的な手順を基盤にして、初めての人がたどる順路をそろえる改善が中心になります。
