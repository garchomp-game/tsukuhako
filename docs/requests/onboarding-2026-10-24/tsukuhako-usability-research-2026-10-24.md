## 1. 調査から得た結論

**ツクハコの最初の案内は、「何ができるようになるか」「今何をするか」「どの状態になれば次へ進めるか」を中心に組み立てるのが適切です。** 内部の管理番号や仕組みを先に学ばなくても、最初の成功まで進めることを目指します。

今回共有された3点について、調査結果は次のように整理できます。

| 共有された改善点 | 調査を踏まえた判断 | 修正方針の候補 |
|---|---|---|
| F2と言われても意味が分からず、利用者が知る必要もない | 利用者の目的に結びつかない内部識別子を、通常の選択や手順の前提にする必要はない | 目的が分かる表示名を使う。内部IDが必要なら開発・診断用の詳細へ残す |
| devcontainerがインストール前の準備にある | 生成される設定と、それを動かすソフトを分けて判断する必要がある | ツクハコが作る設定の事前準備は求めない。拡張機能・実行環境の必要性は自動化範囲を確認して整理する |
| 最初のマニュアルは、何をするかの案内に絞りたい | 操作の案内と背景説明を分ける方向は、国内外の指針と整合する | 主な手順に操作・必要条件・結果・復帰先を残し、仕組みや比較は任意の詳細へ移す |

この方針は、利用者の言葉を使うこと、操作と結果を結びつけること、補足説明を分けることに関する指針を、ツクハコへ当てはめたものです。[NN/gのユーザビリティ原則](https://www.nngroup.com/articles/ten-usability-heuristics/)、[SmartHRの操作手順ガイド](https://smarthr.design/products/contents/help-center/step-by-step/)、[デジタル庁のディスクロージャー指針](https://design.digital.go.jp/dads/components/disclosure/)

**評価の中心は、説明が短くなったかではなく、初めての利用者が補足なしで次の操作を選び、結果を確かめられるかです。** 以下の文例や構成は、その検証に向けた提案です。

## 2. 調査の範囲と、事実・提案の区別

### 今回の出発点

利用者本人が実際にツクハコを試して気づいた、用語、事前準備、初回マニュアルの問題を出発点にしました。引き継ぎ資料にある「環境構築で止まっている人が、自分のPCで開発へ進める」という目的も参照しています。

今回はこちらで最新のツクハコを操作したり、現行のコード・配布物・ガイド全文を監査したりしていません。そのため、本人の観察を受け止めつつ、現在の画面文言や自動セットアップ範囲について未確認の部分を残しています。

| 材料 | このレポートでの扱い |
|---|---|
| 今回の本人の利用報告 | 実利用から得られた問題の報告 |
| 2026年10月24日の引き継ぎZIP | 過去の目的・方針・進捗を知る資料。最新実装の証明にはしない |
| 公式デザインシステム、文章作成指針 | 設計・執筆の判断根拠。製品ごとの最適解や効果を保証するものではない |
| VS Code・Development Containers・Dockerの公式資料 | 設定と実行環境の一般的な関係を確認する根拠 |
| このレポートの文例・構成・優先順位 | ツクハコ向けの提案。実装済みの機能・確定した表示名ではない |

### 「日本人ユーザーに分かりやすい」の捉え方

本調査では、日本語で操作する初学者が、案内の言葉と実際の画面を照合しやすいことを重視します。「日本人は全員、説明が多い方を好む」などの国民性を仮定しません。

文化審議会の文章作成指針、国内プロダクトであるSmartHRの指針、デジタル庁の設計指針を、日本語表現と画面設計の参考にしました。これらは日本人と他国の利用者を比較した実験ではありません。英語の語数制限や文末の慣習も、そのまま日本語へ移しません。

## 3. 用語は「目的を理解する言葉」と「操作対象を探す名前」を分ける

### 3.1 F2のような内部IDを、利用のために覚えさせない

Nielsenの原則では、内部の専門用語より利用者に馴染みのある言葉を使い、別の画面で得た情報を覚えておかなくても操作できるようにすることが重視されています。[NN/g：10 Usability Heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/)

ツクハコへの適用では、F2の意味を長く説明する前に、通常の入口からF2を外せないか検討します。

| 情報の種類 | 表に出す条件 | ツクハコでの例 |
|---|---|---|
| 利用者の目的 | 通常の選択・見出しに使う | 「Webアプリを作る準備」 |
| 外部アプリで探す正式名称 | その名前を見つけて操作する場面で使う | 「VS Code」「Dev Containers」 |
| 技術の種類 | 選択に必要なら短い補足へ。背景だけなら詳細へ | 「この構成ではNext.jsを使います」 |
| 内部識別子 | 開発、ログ、問い合わせで必要なとき | 「構成ID：F2」 |

「Webアプリを作る準備」は表示名の仮案です。他の構成も同じ目的なら、それだけでは区別できません。選択肢全体を確認して、作れるものや用途の違いが分かる名称にする必要があります。「かんたん」「おすすめ」だけで内容を代用するのも避けます。

初回用の推奨経路を設ける場合も、他の構成を選ぶ入口は残せます。初めての人に全構成の比較を要求することと、既存機能を削ることは別の判断です。

### 3.2 正式名称が必要な場所では、用途を添えて使う

外部アプリの操作名まで曖昧な日本語へ置き換えると、画面で探せなくなります。文化審議会の指針も、専門用語・外来語について、読み手と必要性に応じた言い換えや説明を求めています。[文化審議会『公用文作成の考え方』解説・印刷頁22–23](https://www.bunka.go.jp/seisaku/bunkashingikai/kokugo/hokoku/pdf/93651301_01.pdf)

例えば、拡張機能の追加が本当に必要な場面なら、次のように書けます。

> VS Codeに、開発環境を開くための機能を追加します。拡張機能の画面で「Dev Containers」を選んでください。

これは構造の例です。公開する手順では、実際のリンク、画面名、表示言語、発行元など、正しい対象を選ぶために必要な情報を照合します。利用者に名前を暗記させる必要はありません。

## 4. Dev Containerの事前準備は、対象物と必要な時点を分けて整理する

### 4.1 「devcontainer」という一語でまとめない

VS Codeの公式資料は、環境の設定を記す `devcontainer.json` と、VS CodeのDev Containers拡張、Dockerなどの実行環境を別々に扱っています。設定ファイルが同梱されていても、それだけでPC側のソフトが導入済みになるわけではありません。[VS Code：Developing inside a Container](https://code.visualstudio.com/docs/devcontainers/containers)

| 対象 | 役割 | 利用者への案内の考え方 |
|---|---|---|
| `.devcontainer` 内の設定ファイル | 開発環境の作り方・開き方を記述する | ツクハコが生成するなら、利用者に事前作成させない |
| VS Code本体 | コードを編集するアプリ | 採用した経路で使うなら、必要になる時点までに用意する |
| VS CodeのDev Containers拡張 | VS Codeから開発用コンテナーを開く | 自動導入されるか確認し、利用者の操作が必要な場合に案内する |
| Dockerなどの実行環境 | コンテナーを作成・実行する | 導入の有無だけでなく、その経路で利用可能かを確かめる |
| WindowsのWSL 2 | 採用したWindows経路でLinux環境を使う | Windowsの該当経路にだけ案内する。Linux向け手順へ混在させない |
| コンテナー内の言語・ライブラリなど | 生成後の環境内で使う道具 | 自動準備するものは利用者の手作業にせず、準備の進行として示す |

補足として、`customizations.vscode.extensions` に指定する拡張はコンテナー内へ追加するもので、PC側で環境を開くための拡張とは区別します。[Development Containers：Supporting tools and services](https://containers.dev/supporting)

WindowsのWSL 2や連携設定の必要性は、選んだ実行経路によって変わります。LinuxにもDocker Desktop以外の経路があります。全OS・全方式の一般論を初回ガイドへ並べず、ツクハコが案内・検証する方式に絞ります。[Docker：WSL 2 backend](https://docs.docker.com/desktop/features/wsl/)、[Docker：Install Docker Engine](https://docs.docker.com/engine/install/)

### 4.2 「いつ必要か」を分ける

推奨する整理は、次の3段階です。

| 段階 | 案内する内容 | 修正前に確認すること |
|---|---|---|
| ツクハコをインストールする | 対応OS、必要な権限など、アプリ導入の条件 | Dockerや拡張が、この段階でも実際に必要なのか |
| 開発用のフォルダーを作る | 作るもの、保存先、既存ファイルへの影響 | ファイル生成だけなのか、ここで外部ツールも実行するのか |
| 作った環境を動かす | 使用するエディター、拡張、実行環境の不足分 | 何を自動で準備し、何を利用者が操作するのか |

**「設定はツクハコが作るので事前準備は不要」という説明は、生成する設定を指すなら自然です。一方、現行案内の「devcontainer」が拡張機能を指しているなら、文言と案内時点を直す判断になります。** 現物を確認してから、削除・移動・自動化を選びます。

なお、VS Codeには、特定の起動リンクから必要な拡張の導入を進める方式もあります。「拡張は必ず手動で導入させる」とも決めつけません。これをツクハコが採用しているか、ローカルの生成フォルダーへ適用できるかは未確認です。[VS Code：Create a Dev Container](https://code.visualstudio.com/docs/devcontainers/create-dev-container)

### 4.3 準備確認を利用者の自己申告だけにしない

以下は、製品側の実装を検討する際の提案です。

- 自動確認できるものは、利用者に専門用語のチェックリストを読ませる前に確認する。
- 結果は「準備できています」「追加が必要です」「起動が必要です」「自動では確認できません」など、次の行動が分かる形にする。
- 検出に失敗しただけで「未インストール」と断定しない。
- すでに準備できている人には、同じ導入を繰り返させない。

Dockerの導入とサービスの起動は別の状態です。このため「導入済み」だけを「使える」と扱わないことには技術上の根拠があります。[Docker：Start the daemon](https://docs.docker.com/engine/daemon/start/)

必要なOS条件、大きなダウンロード、再起動など、利用開始の判断に関係する条件は早い段階で概要を示します。細かな実行手順を後ろへ移すことによって、重要条件を初めて知る時点まで遅らせないようにします。

## 5. 初回ガイドと詳しい説明を分ける

### 5.1 文書を、読む目的で整理する

Diátaxisは、文書を学習、作業、仕様確認、背景理解という異なる需要から整理するモデルです。初回セットアップをその分類へ機械的に押し込める必要はありませんが、作業を進める途中へ長い背景説明を混ぜない考え方は参考になります。[Diátaxis：Start here](https://diataxis.fr/start-here/)

ツクハコでは、次の入口が候補になります。

| 入口の仮案 | 読む人の目的 | 入れる内容 |
|---|---|---|
| はじめて使う | 最初の画面を表示する | 一つの推奨経路、必要な操作、完了の目印 |
| やりたいことから探す | 二回目以降の作業を進める | 別の構成を作る、保存先を変える、再び起動する |
| 困ったとき | 止まった所から復帰する | 症状別の確認と対処 |
| 仕組みを知る | 技術や設計の理由を理解する | Docker、WSL、Dev Containerの役割など |
| 対応環境・設定を調べる | 条件や仕様を確認する | 対応OS、構成一覧、設定項目、確認済みの範囲 |

これは五つのファイルを新設する指示ではありません。同じガイド内の節でも実現できます。初回の入口を一つにし、必要な詳細へ行ってから手順へ戻れることが重要です。

### 5.2 最初に残す情報と、後から読める情報

デジタル庁とGOV.UKは、折りたたみを補足に使い、利用に必要な情報まで隠さないよう求めています。短く見せることだけを目的にしない点が共通しています。[デジタル庁：ディスクロージャー](https://design.digital.go.jp/dads/components/disclosure/)、[GOV.UK：Details](https://design-system.service.gov.uk/components/details/)

| 主な手順に残す | 必要な人が開く詳細へ置く |
|---|---|
| 何ができるようになるか | 製品の設計思想、開発の経緯 |
| 今、どのアプリで何をするか | 技術の詳しい仕組み |
| その操作に必要な条件 | ほかの実現方法との比較 |
| 押すボタン、入力する内容 | 推奨経路以外の操作方法 |
| 成功した表示・次へ進める目印 | 全設定項目の解説 |
| 待つ必要があること・待機状態 | 詳細ログ、内部処理の説明 |
| 上書きなど、その場の判断に必要な注意 | 一般的な用語集、追加学習 |
| 止まったときに開く案内 | 個別のまれな症状の長い説明 |

「なぜ必要か」も、すべて取り除く必要はありません。「開発環境を動かすために使います」のような短い理由が判断を助ける場合は残します。詳しい構造説明だけを別へ移します。

### 5.3 折りたたみと別ページの使い分け

短い補足はその場で開き、長い解説は別の節・ページへ移す案が適切です。リンク名は「詳細」だけで済ませず、「Dockerを使う理由」「画面が表示されないとき」のように中身を示します。

すべての手順を順番に読む必要があるのに、タブの中へ分散すると見落とす可能性があります。GOV.UKも、順に読む内容や比較する内容へのタブ使用に注意を促しています。[GOV.UK：Tabs](https://design-system.service.gov.uk/components/tabs/)

## 6. 初回ガイドの構成案

### 6.1 冒頭で、到達点と入口を示す

Diátaxisのチュートリアル指針は、到達点を先に示すこと、小さくても見える結果を得られること、操作の後に何が起きるかを伝えることを重視しています。学習用の文書に対する指針ですが、初回の操作案内にも応用できます。[Diátaxis：Tutorials](https://diataxis.fr/tutorials/)

冒頭の文例：

> このガイドでは、ツクハコで開発用のフォルダーを作り、自分のPCのブラウザーにサンプル画面を表示します。まず、お使いのOSの手順を開いてください。

OSをアプリ側で判断できるなら、そのOSの案内を最初から示す方が自然です。自動判定を使う場合も、誤判定を直せる入口は必要です。対応していないOSを選べるように見せないことも確認します。

「5分で完成」「必ず迷わない」といった表現は、実測や利用者テストなしには付けません。

### 6.2 工程の並べ方

次は全体像を検討するための表です。実際のクリック手順や画面名を確定したものではありません。

| 工程 | 利用者がすること | 次へ進める目印 | 止まったときの入口 |
|---|---|---|---|
| 1 ツクハコを入れて開く | 対象OSの配布物を取得し、案内に沿って導入・起動する | ツクハコの開始画面が表示される | インストールできない／起動できない |
| 2 最初に作るものを選ぶ | 目的が分かる推奨項目を選ぶ | 作成する内容を短い言葉で確認できる | どれを選ぶか分からない |
| 3 開発用のフォルダーを作る | 保存先など必要最小限の入力をして作成する | 作成先と、ファイル作成の完了が分かる | 保存先を選べない／作成に失敗した |
| 4 動かすための準備を確認する | 不足しているソフトや機能だけ用意する | 採用した経路で必要なものを使える | 準備できているか分からない |
| 5 作った環境を開く | 案内されたアプリで環境を開き、初期準備を待つ | 接続に加え、必要な初期処理の正常終了を確認できる | 開かない／準備が終わらない |
| 6 サンプル画面を表示する | 動作開始の操作をし、ブラウザーで開く | 指定したサンプルの表示を確認できる | 画面が出ない／エラーが表示される |

工程4を工程3より前に置く必要があるかは、実装の依存関係と利用者の作業負担で判断します。順番を文章だけで決めず、実際の一巡と合わせます。

「アプリを入れた」「フォルダーを作った」「開発環境が起動した」「初期処理が終わった」「画面が表示された」を一つの「完了」にまとめないことが、この製品では特に重要です。

### 6.3 各手順の基本形

Googleの公式手順ガイドは、一手順一操作を基本とし、場所・操作・結果を対応させます。小さな連続操作をまとめることも認めているため、必ず一クリック一行にする必要はありません。[Google：Procedures](https://developers.google.com/style/procedures)

各手順は、次の情報を必要な範囲で持つ構成を提案します。

1. **見出し**：この段階で何をするか。
2. **操作する場所と操作**：どのアプリの、どの項目を選ぶか。
3. **結果**：どの表示になれば、正常に進んだと分かるか。
4. **進まない場合**：症状に合う案内への入口。
5. **任意の詳細**：仕組みを知りたい人のための参照先。

すべてを毎回五つの囲みとして表示する必要はありません。単純な操作なら、短い一文と結果だけでも足ります。

例えば「保存先を選ぶ」という操作を説明する際には、「フォルダーを選びます」だけで終えず、選んだ場所が画面のどこに反映されたらよいかを添えます。実物にあるボタン・表示に合わせて書くことが前提です。

最初の画面が出た後には、「次回もう一度開く方法」「作業を終える方法」への入口を置く案が考えられます。初回の成功後に読む情報として扱い、最初の手順へ大量に追加しません。

## 7. 日本語の案内を具体的にどう書くか

### 7.1 文と見出し

文化審議会の指針では、結論を早く示し、内容を予測できる見出しを付け、一文に複数の論点を詰め込みすぎないことが重視されています。文の長さの目安を、製品の絶対的な字数制限にする必要はありません。[『公用文作成の考え方』解説・印刷頁31–34](https://www.bunka.go.jp/seisaku/bunkashingikai/kokugo/hokoku/pdf/93651301_01.pdf)

ツクハコでは、次のような執筆ルールを候補にできます。

| 観点 | 提案するルール | 文例 |
|---|---|---|
| 見出し | 内容名だけでなく、その節で行うことを示す | 「生成設定」→「作るものと保存先を選ぶ」 |
| 操作する場所 | アプリをまたぐ手順では、最初に場所を示す | 「VS Codeで、［ファイル］を開きます」 |
| 文の単位 | 一文の中心になる操作・判断を一つにする | 長い条件文を、対象OSと操作の二文へ分ける |
| 主体 | 利用者の操作と、自動処理を区別する | 「［作成する］を押します。ツクハコが設定ファイルを作成します」 |
| 必須・任意 | 実施が必要か分かる表現にする | 「この手順は、別の保存先を使う場合だけ行います」 |
| 完了の目印 | 「正常」「適切」などの抽象語だけにしない | 実際に表示される成功メッセージや画面の特徴を示す |

上表の変更前表現は、問題を説明するための例です。現在のツクハコの文言を転記したものではありません。

### 7.2 表記をそろえ、短縮しすぎない

SmartHRの指針は、内部用語、表現の揺れ、冗長な敬語を避ける一方、助詞を削りすぎることや、漢字を過度にひらがなへ変えることにも注意しています。[SmartHR：基本的な考え方](https://smarthr.design/products/contents/writing-style/)

ツクハコ向けには、少なくとも次の対象について表示用語を決め、アプリ・内蔵ガイド・生成後の案内へそろえることを提案します。

- 作成されるフォルダーの呼び名。
- 作成する構成の名前。
- 作成、起動、接続、初期準備の区別。
- 「準備できています」「確認できません」などの状態名。
- ヘルプ、詳しい説明、問い合わせ先の呼び名。

例えば「フォルダー」「ディレクトリ」「出力先」を同じ意味で無造作に使い分けると、別のものに見える可能性があります。一方、保存する親フォルダーと、今回新しく作るフォルダーは実際に別物なので、統一しすぎて区別を消さないようにします。

### 7.3 ボタン・リンクは、選んだ結果を予想できる言葉にする

SmartHRは、ボタンに実行する操作を、リンクに移動先が分かる文言を用いる考え方を示しています。[SmartHR：その他のUIテキスト](https://smarthr.design/products/contents/ui-text/app-writing/)

| 曖昧になりやすい例 | 文言の候補 | 採用時の条件 |
|---|---|---|
| 実行 | 開発用フォルダーを作成する | 実際に行う処理がフォルダー・ファイルの作成である |
| 次へ | 保存先を選ぶ | 本当に次の画面で保存先を選ぶ |
| OK | 変更を保存する | 保存が発生する操作である |
| こちら | Dockerの準備手順を読む | 移動先がその準備手順である |
| 詳細 | この構成で使う技術 | 開くと技術構成を確認できる |

「次へ」「戻る」のような標準的な語を一律に禁止する必要はありません。周囲の見出しで行き先が明確なら使えます。確定操作やデータを変更する操作では、結果が分かる文言を優先します。

### 7.4 日本語と外部アプリの表示を照合できるようにする

以下は、ツクハコの利用場面に合わせた確認・設計の提案です。

- 日本語版の画面で検証した手順を優先して用意し、確認した表示言語を明記する。外部アプリの日本語化自体を新たな利用前提にはせず、英語版の操作名が必要な場合は、対応する箇所にだけ添える。
- 外部アプリが英語表示のままでも、全部の文章を日英併記にせず、押す項目の対応が分かるようにする。
- 入力例と操作名を、地の文と見分けられる表記にする。コピーするコードやURLは、記号や文字を全角化・言い換えせず原形を保つ。
- 日本語名や空白を含む保存先、IME入力で問題が起きるかを確認する。未確認のまま「日本語は禁止」と条件を追加しない。
- 制限が実際にある場合は、入力前に理由と使える例を示す。許容できる表記は製品側で受け付ける方向も検討する。
- 説明文の長さに合わせて折り返せるようにし、ボタンの日本語が途中で切れないか確認する。

入力に必要な形式や条件を知らせることは、W3CのLabels or Instructionsでも扱われています。説明の過不足の両方を避け、作業に必要な手がかりを与えるという位置づけです。[W3C：Labels or Instructions](https://www.w3.org/WAI/WCAG22/Understanding/labels-or-instructions.html)

### 7.5 画像や位置だけに頼らない

スクリーンショットは、現在の画面と操作場所を照合する補助として使います。対象OS・表示言語・製品版を合わせ、操作名を本文にも残します。

「右下の緑のボタン」だけでは、画面の幅や見え方が変わると探せません。「［作成する］を押します」のように名前を示し、位置や色は補助として添えます。これはW3Cの感覚的な特徴だけに頼らない案内にも整合します。[W3C：Sensory Characteristics](https://www.w3.org/WAI/WCAG22/Understanding/sensory-characteristics.html)

## 8. マニュアルとアプリを一つの流れとして設計する

### 8.1 マニュアルだけ直しても残る問題

今回の報告から、文面だけでなく、次の三層で確認する必要があります。

| 層 | 確認すること | 改善の候補 |
|---|---|---|
| 文言 | 用語、見出し、ボタン、操作説明が理解できるか | F2の表示名、曖昧な準備項目の書き換え |
| 情報の配置 | 今必要な情報を、その場所で見つけられるか | 初回ガイドと詳細の分離、OS別案内、症状別ヘルプ |
| 操作・状態 | 何をすれば進み、どこで終わるか分かるか | 不足の検出、現在地、待機状態、復帰・再開の導線 |

例えば、マニュアルからF2を消しても、アプリでF2を選ばなければ先へ進めないなら不整合が残ります。逆にアプリの名前だけ変えても、生成後のREADMEや案内が旧名称なら迷いが続きます。

通常の利用経路として、受取ページ、インストーラー、開始画面、構成選択、保存先、作成完了、外部アプリへの移動、初期準備、ブラウザー表示、エラー時の案内まで確認対象に含めるのが妥当です。

### 8.2 現在地と、次に必要な操作を示す

デジタル庁のステップナビゲーションは、全体の工程と現在位置を示すためのものです。W3Cの認知アクセシビリティ補足指針でも、完了した工程、現在の工程、残る工程、重要な選択を見えるようにする考え方が示されています。[デジタル庁：ステップナビゲーション](https://design.digital.go.jp/dads/components/step-navigation/)、[W3C：Make Each Step Clear](https://www.w3.org/WAI/WCAG2/supplemental/patterns/o1p04-clear-steps/)

ツクハコでは、例えば次の表示を検討できます。

> フォルダーの作成は完了しました。次に、作った環境をVS Codeで開きます。

ただし、VS Codeで開けたかどうかを検出できないなら、検出済みの完了表示にしません。必要に応じて利用者が確認する段階を明示します。

主に進める操作を目立たせつつ、戻る・中断する・ヘルプを開く操作も見つかるようにします。「一つの主操作を明確にする」ことを、他の選択をすべて消すことにはしません。

### 8.3 長い待ち時間と失敗を見分けられるようにする

初回の環境準備には、ダウンロードや初期処理が含まれる可能性があります。利用者向けには「何を準備中か」「操作せず待ってよいか」「停止・失敗した場合はどうするか」が必要です。

提案例：

- 確認できた処理の段階を、人が理解できる言葉で表示する。
- 総量が分からない処理に、根拠のない残り時間や進捗率を付けない。
- 初期処理を待つ必要があるなら、接続だけで全完了にしない。
- 中断できる場合は、その結果と再開方法が分かるようにする。
- 成功・エラーを、すぐ消える通知だけにしない。

状態変化を読み上げ等の支援技術でも把握できるようにする観点は、W3CのStatus Messagesにあります。ただし、このレポートはツクハコのWCAG適合性を判定する監査ではありません。[W3C：Status Messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)

## 9. 止まったときの案内は、復帰できる形にする

SmartHRは、エラーメッセージを、事象・原因・対処を通じて次の操作へ進めるためのものとしています。[SmartHR：エラーメッセージの基本的な考え方](https://smarthr.design/products/contents/error-messages/overview/)

ツクハコ向けには、次の構成を提案します。

1. 何ができなかったか。
2. 分かっている原因、または確認できた事象。
3. 次に試せる具体的な操作。
4. 解決しない場合の相談先・確認情報。

文例：

> 開発環境を起動できませんでした。Dockerに接続できません。お使いのOSの確認手順を開いてください。

この文例を採用できるのは、「Dockerに接続できない」ことを確認できた場合です。接続できない原因が不明なのに「Dockerがインストールされていません」と断定しません。OSが分かる場所では、そのOSの対処へ直接案内できます。

利用者が入力を直せる問題と、製品側・通信先の問題は区別します。無条件の再実行を勧める前に、作成済みファイルへの影響も確認します。技術ログは問い合わせ用の詳細へ分け、利用者がログの意味を理解しなくても相談できる形にします。

「困ったとき」は、利用者が見て分かる症状から探せるようにします。例えば「画面が表示されない」「準備が終わらない」「保存先を選べない」です。「Docker daemon」「postCreateCommand」など、原因を知っていないと選べない名前を入口にする必要はありません。

診断情報をコピーする仕組みを用意する場合は、内容を確認できるようにし、秘密情報を含めない設計も確認します。これは問い合わせ導線に関する提案で、現在その機能があるという意味ではありません。

## 10. 改善できたかを確かめる方法

### 10.1 対象に近い人の操作を観察する

GOV.UKのユーザビリティテストの指針は、実際または想定される利用者に具体的な課題へ取り組んでもらい、理解と操作を観察する方法を示しています。課題文で正解のボタンや操作経路を教えないことも重視しています。[GOV.UK：Using moderated usability testing](https://www.gov.uk/service-manual/user-research/using-moderated-usability-testing)

ツクハコなら、課題は次のように設定できます。

> ブラウザー上でプログラミングを学んできました。今度はこのPCでWebアプリを作り始めたいと考えています。ツクハコと同梱の案内を使い、最初のサンプル画面を表示してください。

「F2を選び、Dev Containerを開いてください」とすると、問題にしている用語や経路を試験側が教えてしまいます。

まず少人数で問題発見のための試行を行い、直してから再確認する案が現実的です。例えば3〜5人から始めるとしても、それは今回の作業規模の案であり、「5人なら全問題を発見できる」という保証ではありません。

### 10.2 観察する項目

| 観点 | 記録すること |
|---|---|
| 最初の理解 | 何ができると思ったか、最初にどこを選んだか |
| 用語 | 意味を調べたり、質問したりした言葉 |
| 準備 | 自分で用意するものと、自動で用意されるものを区別できたか |
| 手順 | 次の操作を探して止まった場所、見落とした案内 |
| 結果 | 何を見て成功・未完了と判断したか |
| 復帰 | エラー時に対処を見つけ、続行できたか |
| 補助 | どの場面で、どんな説明や操作代行が必要だったか |
| 時間 | 操作に使った時間、迷った時間、処理待ち時間を区別 |
| 最終結果 | 支援なし完了／支援あり完了／未完了と、その理由 |

考えを声に出してもらう場合、通常利用より時間がかかる可能性があります。そのため、その時間をそのまま販売用の所要時間へ転用しません。主観的な「分かりやすかった」という感想に加え、実際の停止や補助の有無を記録します。

### 10.3 確認環境と結果を分けて残す

次の違いを記録すれば、改善の効いた場所と残る問題を判断しやすくなります。

- 既に必要なソフトが揃っているPCか、準備が足りないPCか。
- LinuxとWindowsのどちらか。確認したOS、アプリ版、案内の版は何か。
- 初めて使う人か、製品を知っている作者・開発担当か。
- 利用者が自力で進めたか、途中で人やAIが補ったか。
- 日本語表示、英語表示、拡大表示、キーボード操作など、どの条件を確認したか。

すべてを一度に網羅する必要はありません。初回に提供する経路から確認し、未確認の条件は未確認として残します。

### 10.4 修正後の評価に使える観点

以下は、将来の修正依頼に落とし込むための評価候補です。今回の時点で、実装受入条件として確定したものではありません。

| 評価したいこと | 確認のしかた |
|---|---|
| 内部IDの理解なしに進める | 通常の入口・選択・生成後の案内を通し、F2の意味を質問しなくても目的を達成できるか観察する |
| 事前準備の役割が明確 | 利用者が行う準備と自動処理を説明できるか、実際の不足案内と照合する |
| 詳しい解説を読まなくても初回操作ができる | 背景説明を開かず、主な手順だけで進めるか確認する |
| 各段階の結果が分かる | 利用者に「今どこまで終わったと思うか」を確認し、実際の状態と照合する |
| 外部アプリへの移動で迷わない | 移動先、対象フォルダー、続きの手順を自分で見つけられるか観察する |
| 止まっても次の行動を選べる | 代表的な失敗条件で、案内から確認・復帰・相談へ進めるか試す |
| アプリとガイドの言葉が一致する | 表示名とリンク先を確認し、利用者が同じ対象として認識できるか確かめる |

## 11. 修正依頼へ進む前に整理する項目

### 11.1 今回の調査から優先したいこと

| 優先 | 項目 | 理由 |
|---|---|---|
| 先に整理する | devcontainerの意味と、準備の必要時点 | 必要な準備まで削ること、不要な準備を要求することの両方を避ける |
| 先に整理する | 初回の一巡と、各段階の完了判定 | 文面の改善だけでは埋まらない操作上の不足を見つける |
| 最初の改稿で扱う | F2などの表示名、目的を示す見出し | 利用者が選択する時点の理解を助ける |
| 最初の改稿で扱う | 初回手順と背景説明の分離 | 主な操作へ集中しながら、詳しく学ぶ入口を残す |
| 同じ改修で照合する | アプリ・ガイド・生成後案内の用語と順番 | 一か所だけ直したことによる不整合を防ぐ |
| 操作確認を見て判断する | 自動検出、直接起動、再開、診断情報の機能 | 実装の必要性と効果を、実際の停止箇所に基づいて判断する |

この優先順位は調査に基づく提案です。本人がこれから共有する他の問題によって追加・変更できます。

### 11.2 現物で確認する必要があること

1. 「devcontainer」と表示されている具体的な場所と、その項目が指すもの。
2. 現行版が生成・導入・起動・検出するものと、利用者が操作するもの。
3. F2が出る画面、内蔵ガイド、生成物、問い合わせ表示の範囲。
4. 最初の推奨構成が実際に提供するものと、他構成との違い。
5. 配布物の取得からサンプル画面までの実際の経路。
6. 起動・接続・初期処理終了を判断できる、実際の表示と状態。
7. 日本語表示の外部アプリと、現行ガイドの画面名の対応。

これらは次の修正依頼を具体化するための確認項目です。すべてを本人への質問にする必要はありません。作業担当がコードや配布物で確認できる点と、本人の意図を確かめる点を分けます。

### 11.3 依頼資料に変換するときの構成

後続の資料では、各問題を「観察した場面 → 利用者が困ること → 目指す状態 → 修正範囲 → 確認方法」で整理すると、作業担当へ意図を伝えやすくなります。

今回のレポートは、そのための原則と根拠までをまとめたものです。修正依頼の作成・送付、製品の変更、インストール、公開は行っていません。
