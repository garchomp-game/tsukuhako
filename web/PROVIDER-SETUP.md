# 本番配信へ接続する前の手順

2026-10-22。**ここに記載する本番操作は今回未実施です。** 現実装はローカルpreviewとMock受信箱だけで、本番sender adapter、署名付きwebhookの受信、定期実行、運営用の認証は未実装です。APIキーやドメインを設定するだけでは実配信へ切り替わりません。

## 1. 利用する方式と費用を決める

初回シリーズはResendの [Automations](https://resend.com/docs/dashboard/automations/introduction)、号ごとの定期便は [Broadcasts](https://resend.com/docs/dashboard/broadcasts/introduction) を候補とします。Automationsはイベントを起点に段階的な処理、Broadcastsは連絡先への号の送信を扱います。公開資料で機能の存在を確認した段階であり、自アカウントでの利用可否は未確認です。確認メールは学習便と別のtransactional用途として扱います。

自アカウントの権限・プランで次の条件を対応付けてください。満たせる部分は事業者の機能を使い、不足する条件だけ本番adapterで補います。事業者の管理画面を作り直すことは目的にしません。

| この試作のルール | 本番で確認する点 |
|---|---|
| 同意＋本人POST確認で初回開始 | GET先読みや購入者ページの閲覧だけでは開始しない。イベントは一意 |
| 初回直後、確認日の2/5日後19:00 JST | 日付基準、タイムゾーン、UTC境界を実サービスへ対応付ける |
| 定期便は7×24時間以上＋初回未送信なし | 号の承認と対象者を分け、原稿がない週は送らない |
| 学習/定期の合計はJST暦日1通 | 複数の配信方式を使っても同じ枠を共有する。unknownも照合まで枠を保持 |
| 解除・苦情・永久バウンス後は抑止 | 予約時だけでなく最終受付前に確認。登録入力で抑止を解除しない |
| 版変更後は再確認 | 件名・本文・対象・リンク・フッター・対応ガイドの版と承認を結び付ける |
| 遅延・全体停止 | 古い便をまとめない。停止解除で旧予約を戻さない |

不足がある場合だけ、D1の配送一意制約と排他的な取得、Workersの定期実行と `/emails` 等を組み合わせる別実装を検討します。現在のローカルAPIをそのまま公開する構成ではありません。

[Resend料金ページ](https://resend.com/pricing)は `/emails` の通数とBroadcastsの連絡先数を別の基準として説明しています。Automationsの利用条件、確認メールを含む通数、Contacts数、超過、日次上限、ログ保持、停止方法を自アカウントで確認し、月額上限を記録します。Cloudflare側の利用量・保持容量も加えて判断してください。今回、金額の確定、契約、課金は行っていません。

## 2. 送信元・公開先・秘密情報を用意する

本人が送信用ドメイン、From表示名/アドレス、Reply-To、問い合わせ担当、公開ガイド/登録/プライバシーURLを確定します。送信ドメインは所有権を確認し、Resendの [ドメイン追加手順](https://resend.com/docs/add-a-domain) に表示されるSPF/DKIMのDNS値を使います。値をこの文書から推測して登録しません。DMARC方針も確認し、実メールの認証結果・From・Reply-Toが決定と一致するか試験します。

APIキーとwebhook signing secretは、将来のサーバー側secretへ保存します。[Workers secrets](https://developers.cloudflare.com/workers/configuration/secrets/) を使い、`VITE_*`、公開JS、メールMarkdown、リンク設定、Gitへ入れません。今回の `.env.example` はローカル設定の説明であり、本番キーを読み込む実装はありません。

本番用D1と検証用D1、ドメイン/環境、運営者権限、バックアップ・保持/削除・障害時担当を決めます。previewの仮想時計、運営API、受信箱を本番へ移植しません。確認/解除tokenをアクセス解析・ログ・外部リンクへ漏らさず、no-store/no-referrerと先読みで状態を変えない扱いを保ちます。

## 3. 受付・到達・不明を分ける

本番adapterは承認済みの原稿と設定を版に固定し、未解決変数や未承認版を拒否します。各配送ID・原稿revision・対象enrollment・予定時刻と、事業者の受付IDを保存してください。読者ごとに原稿承認を繰り返す必要はありません。

`accepted` は事業者が要求を受け付けた状態です。Resendの `email.delivered` も受信側メールサーバーへの到達であり、本人の閲覧ではありません。受付、到達、開封を同じ成功として記録しません。[イベントの意味](https://resend.com/docs/webhooks/event-types)。

タイムアウト後は `unknown` とし、事業者の受付ID・同じ配送の記録・署名済みイベントを照合します。受付済みなら再送せず状態を確定し、受付前の失敗と確認できた場合だけ明示的に再試行します。確認できないものは保留します。[Resendの冪等性キー](https://resend.com/docs/dashboard/emails/idempotency-keys) は保持期間付きです。現在の公式説明は24時間なので、その期間を超えたunknownを新しいキーで自動再送してはいけません。本番接続時に期間と適用APIを再確認します。

## 4. 解除・苦情・バウンスを受ける

現在の `/api/mail-events` はローカルfixture用です。本番では [公式webhook検証](https://resend.com/docs/webhooks/verify-webhooks-requests) に従い、JSONへ変換する前のraw body、署名ヘッダー、時刻、signing secretを検証してから処理します。無効な署名・過去の再生を拒否し、イベントIDの重複を排除します。記録と抑止を一つの処理として確定し、途中失敗は再試行可能にします。

`email.complained` / `email.bounced`、連絡先や配信テーマの解除・抑止イベントなど、採用方式が出すイベントをローカルの状態へ対応付けます。署名済みの到達イベントが後から来ても、解除・苦情・永久バウンスの抑止を取り消しません。[Resendのイベント一覧](https://resend.com/docs/webhooks/event-types)。

解除は事業者の対応機能を優先します。Broadcastsには受信者別の解除リンクがあり、Cの `{{unsubscribeUrl}}` を事業者側の変数へ置き換えるadapterが必要です。C原稿をそのまま貼るだけで変数が解決するとは扱いません。[Broadcast解除リンク](https://resend.com/docs/dashboard/broadcasts/editor#broadcast-unsubscribe-link)。

本文の解除リンクは、GETで確認画面を開き、本人のPOSTで停止します。メールソフトが行う正規のワンクリック解除POSTは、ログイン・Cookie・追加確認を求めずに処理します。[RFC 8058](https://www.rfc-editor.org/info/rfc8058/) に沿い、HTTPS URL、List-Unsubscribe/List-Unsubscribe-Post、対象ヘッダーを含むDKIM署名、リダイレクトなしのPOST処理を実メールで確認してください。現在のlocalhostのform POST試験は、この本番対応の完了ではありません。

## 5. 明示的な実施指示を受けた後に試験する

公開・DNS変更・契約・実宛先へのテスト送信は今回行いません。本番adapterの実装・レビューと、実施する環境/宛先を本人が指定した後、次を行います。

1. 一般読者名簿を入れず、許可された運営者の試験宛先だけを使う。対象サービス、費用上限、実行期間、停止担当を記録する。
2. 確認メールの表示、期限、先読みGET、本人POST、同じ確認の反復を確認する。HTML/text、送信元、返信先、到達先フォルダも見る。
3. 初回の時刻・日次枠・定期の対象外条件を、サービスの検証方法で確認する。実日程の予約は試験対象だけに限定する。
4. 予約後の解除、正規ワンクリックPOST、未着/再送、事業者が用意するバウンス/苦情の試験、イベント重複/順不同を確認する。実際の苦情を起こすことを試験方法にしない。
5. unknownの照合と全体停止を確認し、事業者の記録と配送IDを対応させる。停止後の未受付メールがなく、再開で旧予約が復活しないことを確かめる。

緊急時は、新規受付と最終送信の入口を停止し、事業者側のAutomation/Broadcast/予約も停止・取消します。どちらか一方の停止だけで完了とせず、処理中と受付済みの範囲を照合します。受付済みメールは取り消せない場合があるため、その範囲を残し、unknownを一括再送しません。再開は原因と抑止状態を確認してから、承認済みの新しい予定だけにします。
