操作可能な初期画面まで約474ms。240回の章切替応答は中央値22.9ms、観測最大64.2ms。60回ごとに5秒休止し、最後は30秒待機。手前に10秒の生成画面待機も含みます。

generation欄は短いGUI生成と6構成IPC生成を含む観測期間の最大値です。100ms間隔の間に生じた真のピークを保証しません。chapter-switchesは複数ブロックをまとめています。CPU差分の一部には間の休止時間も含むため、ブロック別の詳細は生のJSONを参照してください。

DOMと本文キャッシュの上限を実装し、反復測定しましたが、途中のPSSはGC・画像・コード読込などで変動しています。この短時間試験だけで長時間のリーク不在や上限値は断定しません。

同じF2プロジェクト・実VS Code・Docker・ブラウザの下で、各30回、1秒間隔で全プロセスツリーを測定しました。0.3.0は生成画面、0.4.0は教材表示なので活動は同一ではありません。削減量の宣伝や厳密な性能比較には使いません。両版の終了後もCodeとサンプルHTTPの生存を確認しました。

DockerのF2コンテナ観測: `1.385GiB / 23.23GiB`。これはcgroupの使用量で、PSSとは定義が違います。足し合わせて全体PSSと呼びません。

初期baseline-030.jsonは変更前に採ったElectron app.getAppMetricsの参考値で、zygote等を網羅しません。上表の/proc全ツリー測定と直接比較しません。Windows/macOSは測定用実機がなくNOT_RUNです。

終了中の診断では、SIGTERMを無視する所有コマンドの停止を待ち、約1秒で終了しました（app-diagnosis-shutdown.json、固定待機700msを含む）。ヘルパーactive jobの終了も別途確認しました。

再測定する場合は専用プロファイル・生成先を新しくし、CPU/OS/常駐アプリ/開く教材/同時コンテナを記録してください。測定のためにユーザーのプロジェクトや既存Docker資源を削除しないでください。
