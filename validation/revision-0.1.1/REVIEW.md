## 結論

**試作品として受領し、修正と利用者試用へ進める状態です。一般向け配布の完了判定はまだ出しません。**

必須6構成、追加のS3、個別ZIP、教材、既存プロジェクト判定器、新規ジェネレーター、検証証拠が揃っています。個別ZIP7個の全291ファイルについて、同梱ソース・manifest・catalogのハッシュと一致しました。ジェネレーターは構想だけでなく実装済みで、今回の再実行も成功しました。

配布前に直す主な点は次の3件です。

1. 既存プロジェクト判定器の optionalDependencies 検査漏れ。
2. S2のCIで開発サーバーの終了を保証できない処理。
3. B1/S1の自作教材で必要なファイル追加手順が抜けている点。

配布テンプレート本体の最短起動がすべて失敗する、という結果ではありません。各問題が影響する機能を以下に限定して記載します。元ZIPと展開ソースは変更していません。

## R1：既存プロジェクト判定器がローカルoptional依存を見落とす（P2）

**箇所**

- `existing-project-adapter/src/adapter.mjs` 143行：検査用のdeclaredがdependenciesとdevDependenciesのみ。
- 同162–164行：optionalDependenciesはpackage/lock一致だけを確認。
- 同166–170行：ローカル参照・link・版範囲の検査対象にoptionalDependenciesが入らない。

**再現**

1. 付属F2のpackage.jsonと完全なlockfileを基に、隔離したNextプロジェクトを作る。
2. 兄弟フォルダにlocal-helperを置き、optionalDependenciesへ `"local-helper": "file:../local-helper"` を追加する。
3. npmで整合するlockfileを生成する。lock内には `resolved: "../local-helper", link: true` がある。
4. アプリがそのhelperをimportする状態でinspect、preview、applyを実行する。

観察結果：

```json
{
  "applySupported": true,
  "reasons": [],
  "apply": "applied"
}
```

生成されたComposeは対象プロジェクトだけを/workspaceへmountし、兄弟helperは含めません。READMEの「ローカル・git等の直接依存は自動適用対象外」という範囲とも一致しません。今回確認したのは**対応可否の判定漏れ**です。コンテナ内での実ビルド失敗までは再実行していません。

**修正依頼**

- optionalDependenciesも直接依存の検査へ含める。同名依存が重なる場合のnpmの扱いも考慮する。
- file/link/workspace/git等、初版の対応外となる参照を理由付きで拒否する。
- 対象外の場合に適用せず、利用者のpackage/lockやコードを変えない方針を維持する。

**修正後の確認**

今回のローカルoptional依存fixtureは対応外となり、既存の対応可能なNext fixtureは引き続き通ること。OS限定など通常のoptional依存についても、単純な検査追加によって誤判定しないよう扱いを明記する。

## R2：S2のCIで開発サーバーの終了を保証できない（P2）

**箇所**

- `starter-templates/S2/.github/workflows/check.yml` 27–35行。
- `starter-templates/S2/playwright.config.ts` 6行。

HTTP試験用に `npm run dev &` を起動し、trapでnpmのPIDだけをkillしています。配下のサーバープロセスの終了を待つ処理がありません。その後のブラウザ試験はCI環境では既存サーバーの再利用を拒否します。

**今回の再現と限界**

隔離した一時フォルダで、同じnpm起動・trapを使い、npmからNodeの常駐子プロセスを起動しました。

```json
{
  "shellExit": 0,
  "childSurvivesNpmTrap": true
}
```

再現用プロセスは清掃済みです。これは終了処理の不足を示します。**実NextやGitHub上でCI全体が失敗した、とは主張しません。** Nextが3000番で残った場合、次のPlaywright試験がそのサーバーを拒否する構造になっています。

F1/F2/B1/S1の試験は同じ処理を使っておらず、S3にもこの手動起動処理はありません。

**修正依頼**

HTTP試験とブラウザ試験を一つの管理されたサーバーで実行するか、サーバーを直接管理し、終了完了まで待つ処理に統一する。既存サーバーを無条件で再利用する変更だけで済ませないこと。

**修正後の確認**

- CI相当の環境変数・順番で「HTTP試験→ブラウザ試験→build」を連続実行する。
- サーバーを引き継がない境界では、対象プロセス終了とポート解放を確認する。
- 実GitHub Actionsを動かさない場合は、引き続き実CIをNOT_RUNと記載する。今回の依頼をGitHubへの公開許可とは扱わない。

## R3：B1/S1の自作教材に必須ファイルの追加手順がない（P2）

**箇所**

- `starter-templates/B1/docs/BUILD-YOUR-OWN.md` 7–8行。
- `starter-templates/S1/docs/BUILD-YOUR-OWN.md` 7–8行。

教材ではapp/を追加して実行へ進みますが、次のファイルを追加する段階がありません。

|構成|必要な追加|参照元|
|---|---|---|
|B1|`lib/preview.ts`|`app/api/preview/route.ts`|
|S1|`lib/preview.ts`|`app/api/preview/route.ts`|
|S1|`components/PreviewForm.tsx`|`app/practice/page.tsx`|

教材の手順1〜4で明示されたファイルだけを別フォルダへ配置すると、B1は1件、S1は2件の相対import先が欠けました。元の配布テンプレートにはファイルがあるため、**最短起動ではなく「空フォルダから自作する演習」の問題です。**

**修正依頼**

- BUILD-YOUR-OWNを構成別の手順にし、依存するlib/componentsを追加する順番を明記する。
- 各段階で「何を確認できれば次へ進むか」を短く示す。
- F1に存在しないPostCSS設定など、共通文の流用による不要な指示も整理する。

**修正後の確認**

完成版のフォルダを丸ごとコピーせず、修正した教材の手順だけで新しい空フォルダを組み立て、checkと主要操作まで実行できること。

## 小さな追加確認

### 適用記録を編集した場合のundo（P3）

`.devcontainer/.adapter-record.json` にuserNoteを追加した後undoすると、`undone / preserved: []` となり記録も削除されました。対象はadapter自身の管理ファイルで、アプリの編集内容を消したという結果ではありません。

`existing-project-adapter/src/adapter.mjs` 339行と358–359行、およびREADMEの「編集・追記を保持」という表現の範囲を揃えてください。管理記録も編集検出して保持する方法、または管理ファイルの扱いを明確にする方法が考えられます。通常の生成設定を利用者が編集した場合の保護は維持してください。

### F1のESLint固定理由（P3）

F1のVALIDATION末尾には「採用Next設定との互換性」とありますが、F1はVite構成です。F1に実際に当てはまる固定理由へ直してください。

Next系では、lockfileにあるeslint-plugin-import、eslint-plugin-jsx-a11y、eslint-plugin-reactのpeer範囲がESLint10を含まないことを確認しました。ESLint警告を理由に、全構成を未検証の版へ一括更新する必要はありません。

## 残っている確認

### S2の最終配布版からの新規起動

同梱記録には初期版の新規展開試験と、最終ZIPを既存の試験コピーへ再展開した確認があります。最終ZIPそのものを、新規パス・新規ID・空DBで最初から通した証拠はまだ閉じていません。

R2等を修正してZIPを再作成した後、その新しい最終版で次を1回確認してください。

- 日本語・空白入りの新規展開先と新規プロジェクトIDを使う。
- 専用の空DBでconfigure→診断→DB start→Dev Container→migration/seed→メモCRUDを確認する。
- 再読込と通常の停止・再開後にデータが保持されることを確認する。
- 配布ZIPのSHA-256、コマンド、結果、使ったDBの初期状態を記録する。

ホスト全体のcache消去やpruneは不要です。既存の利用者データや他プロジェクトを使わないでください。

### VS Code・Windows/WSL・初学者試用

- VS Code実画面で、F2とS2を代表としてReopen、編集反映、再接続、Rebuildを確認する。
- Windows＋WSLを「検証済み」として案内する前に、その環境で展開場所・Docker連携・起動手順を確認する。
- 試作品を初学者に試してもらう段階では、つまずいた場所と所要時間を記録する。制作者の手順成功だけから教材の分かりやすさを確定しない。

S3の実クラウド接続は接続先未提供でBLOCKEDのままで構いません。追加テンプレートのこの不足を理由に、必須6構成全体の修正を止める必要はありません。

## 家のCodexへ渡す実行依頼

このレビューを追加の修正依頼として、現在の実装を継続してください。

1. R1〜R3を修正し、P3の記述・管理記録の扱いも確認する。
2. 修正の影響範囲に絞って、上記の再現fixtureと受入条件を確認する。
3. S2は修正後の最終ZIPを新規パス・新規ID・空DBから検証する。
4. 変更した構成の個別ZIP・manifest・catalog・検証記録・REPORTを更新し、全体ZIPを作る。ハッシュは実際に渡すZIPと一致させる。
5. 未実施の実機・GUI・クラウド・実CIは、そのままNOT_RUN/BLOCKEDとして残す。
6. 返却レポートは、各指摘の修正箇所、再現試験の結果、未確認事項を短くまとめる。

今回の目的は、現行試作品の確実な引渡しです。GUI追加やテンプレート追加はこの修正に含めません。利用者の実プロジェクトへの適用、外部公開・販売、GitHubへのpush、クラウド作成は行わないでください。
